## 1. Objetivo
Construir una sola vez lo que comparten todos los módulos: request ID, logs, errores, validación, cabeceras de seguridad y transacciones.

## 2. Qué hizo el agente
- **Request ID** (`common/request-id/`): middleware de Express registrado con `app.use` antes del router de Nest, así también cubre las rutas inexistentes. Acepta el `X-Request-Id` del cliente solo si cumple `^[A-Za-z0-9._-]{1,64}$`; si no, genera un UUID. Lo guarda en `req.id` y lo devuelve en el header.
- **Errores** (`common/errors/`): `ERROR_STATUS` con todos los códigos de spec §8 y su estado HTTP, `AppError(code, message)` (sin dependencias de Nest, usable desde el dominio) y `HttpExceptionFilter` global (`@Catch()`). Responde siempre `{ error: { code, message, requestId } }`: `AppError` con su código, `HttpException` 401/403/404 como `UNAUTHENTICATED`/`FORBIDDEN`/`NOT_FOUND`, otros 4xx como `VALIDATION_ERROR` y todo lo demás como 500 `INTERNAL_ERROR`. El detalle del error va solo al log.
- **Validación** (`common/validation/`): `ValidationPipe` global con `whitelist`, `forbidNonWhitelisted` y `transform`; su `exceptionFactory` lanza `AppError('VALIDATION_ERROR')` con la lista de campos.
- **Logs** (`common/logging/`): pino con `nestjs-pino`, en JSON. Cada petición genera una línea con `requestId`, `req.method`, `req.url`, `res.statusCode` y `durationMs`. Los serializadores solo exponen esos campos, así que cabeceras y cuerpos no llegan al log, y además se redactan `authorization`, `cookie`, `set-cookie`, `password`, `passwordHash`, `currentPassword`, `newPassword` y `token`. Los logs de arranque de Nest también salen por pino.
- **`configureApp()`** (`common/configure-app.ts`), compartido por `main.ts` y las pruebas: logger, request ID, helmet, `cookie-parser`, prefijo `/api`, shutdown hooks y Swagger en `/api/docs`.
- **`CommonModule.forRoot()`**: registra el logger, el filtro (`APP_FILTER`) y el pipe (`APP_PIPE`). No depende de la base, así las pruebas no necesitan PostgreSQL.
- **Transacciones** (`common/transaction/`): interfaz `TransactionRunner` + `TransactionContext` con token `TRANSACTION_RUNNER` (los services dependen de la interfaz). Implementación `PrismaTransactionRunner` sobre `prisma.$transaction`, con `ctx.advisoryLock(key)` → `SELECT pg_advisory_xact_lock(hashtextextended(key, 0))`. Helper `prismaTx(ctx)` para que solo los repositorios Prisma accedan al cliente transaccional. `TransactionModule` global.
- **Pruebas**: `test/platform.spec.ts` levanta una app Nest con `CommonModule` y un controlador de prueba (`test/support/platform-test.controller.ts`, fuera del código de producción) y la prueba por HTTP con el `fetch` nativo. `prisma-transaction-runner.spec.ts` prueba commit, rollback y advisory lock con un Prisma simulado. CA6 se verificó además contra PostgreSQL real (§5).

## 6. Desvíos del plan
- **Pruebas HTTP con el `fetch` nativo de Node 24** en lugar de `supertest`, para no agregar otra dependencia. La app de prueba escucha en un puerto libre de `127.0.0.1`.
- **CA6 contra la base real con un script de un solo uso** (`docker compose exec -T api node -`) y no con una prueba automática: la infraestructura de pruebas de integración (`api-test`) llega en T06. El script quedó fuera del repositorio; su salida está en §5.
- **`CommonModule.forRoot({ logStream })`**: el destino de los logs es configurable solo para que la prueba de CA5 pueda leerlos.

## 7. Ambigüedades encontradas
- **`X-Request-Id` enviado por el cliente:** el spec no dice si se respeta. Opción conservadora: se acepta solo si tiene de 1 a 64 caracteres `[A-Za-z0-9._-]` (evita inyección en logs); si no, se genera un UUID.
- **Otros 4xx de Nest o Express** (JSON mal formado, 405, 413…): el spec solo enumera códigos por estado. Se responden con su estado HTTP y código `VALIDATION_ERROR`. El JSON mal formado es 400.
- **Mensajes de error por defecto** en español (`NOT_FOUND`, `UNAUTHENTICATED`, `FORBIDDEN`, `VALIDATION_ERROR`, `INTERNAL_ERROR`): el spec no los fija.
- **Clave del advisory lock:** el spec habla de lock "sobre la fecha" y "sobre el `userId`". `advisoryLock` recibe un texto y lo convierte con `hashtextextended(key, 0)`. Las tareas que lo usen (T05, T05a, T05b) deben usar prefijos distintos, por ejemplo `date:2030-01-07` y `user:<uuid>`.
- **Swagger y el guard global de T03:** `/api/docs` lo sirve Express directamente, fuera del router de Nest, así que el `JwtAuthGuard` global no lo cubrirá. El spec pide Swagger en `/api/docs` pero CLAUDE.md dice que solo login y health son públicos. Queda para revisar en T03.
- **Log de los healthchecks:** Docker consulta `/api/health` cada 5 s y cada consulta genera una línea de log. No se filtró porque el spec pide log de toda petición.
