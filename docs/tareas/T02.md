## 1. Objetivo
Persistir usuarios, salas, reservas, cierres y auditoría con las garantías de base de datos (sin choques, auditoría inmutable) y un seed idempotente.

## 2. Qué hizo el agente
- Instaló Prisma **7.10.1** (CLI, cliente y adaptador `@prisma/adapter-pg`) y bcryptjs 3.0.3, con versiones exactas.
- `prisma/schema.prisma`: modelos `User`, `Room`, `Booking`, `Closure` y `AuditLog` en `PascalCase` con `@@map` a `snake_case`, campos `camelCase` con `@map`, los enums `Role`, `Equipment`, `BookingStatus` y `AuditAction`, IDs `uuid` con `gen_random_uuid()`, `timestamptz` e índices de §7. El generador `prisma-client` escribe el cliente en `src/generated/prisma` (CommonJS), que no se versiona y se genera en el build.
- `prisma.config.ts`: rutas del esquema y de las migraciones, y `DATABASE_URL` tomada del entorno.
- Migración `20261115142500_init`: SQL generado con `prisma migrate diff --from-empty`, más SQL propio con `rooms.equipment NOT NULL`, el índice único `lower(name)`, los CHECK `capacity BETWEEN 1 AND 100`, `attendees >= 1` y `end_at > start_at`, y el CHECK de `email` en minúsculas.
- Migración `20261115142600_bookings_no_overlap`: SQL de spec §7 tal cual (`btree_gist` + `EXCLUDE USING gist`).
- Migración `20261115142700_audit_logs_immutable`: función y trigger `BEFORE UPDATE OR DELETE OR TRUNCATE ... FOR EACH STATEMENT` que lanza excepción.
- `prisma/seed.ts`: usuarios con `upsert` por email y `update: {}`, contraseñas con bcryptjs (10 rondas) tomadas de `SEED_ADMIN_PASSWORD` y `SEED_USER_PASSWORD`. Las 5 salas de S-07 se crean con `createMany` solo si la tabla está vacía. No toca `audit_logs`, reservas ni cierres.
- `src/prisma/` (`PrismaModule` global y `PrismaService` con adaptador pg y `ping()`), y `HealthService`: `GET /api/health` ejecuta `SELECT 1`. El controller no importa Prisma.
- Arranque: `docker-entrypoint.sh` ejecuta `prisma migrate deploy` → `node dist/seed/prisma/seed.js` → `exec node dist/main.js`. El build genera el cliente y compila api y seed (`tsconfig.seed.json`).
- Compose: `DATABASE_URL` con valor por defecto y `start_period` del healthcheck de `api` a 30 s.

## 6. Desvíos del plan
- **Prisma 7.10.1 y no la etiqueta `latest` de npm,** que apunta a `8.0.0-rc.33`, una versión candidata. Prisma 7 exige `prisma.config.ts`, el generador `prisma-client` con `output` y un *driver adapter* (`@prisma/adapter-pg`).
- **El seed se compila con `tsc` a `dist/seed/`** (`tsconfig.seed.json`) en lugar de ejecutarse con `tsx` o `ts-node`. Así la imagen final no necesita herramientas de TypeScript.
- **Trigger de `audit_logs` por sentencia y también contra `TRUNCATE`.** El backlog pide `BEFORE UPDATE OR DELETE`. Por fila, un `UPDATE` o `DELETE` sin filas afectadas no fallaría, y `TRUNCATE` se saltaría el trigger.
- **CHECK `email = lower(email)` y `rooms.equipment NOT NULL`:** están en las restricciones del spec §7 pero no en la lista del backlog. Prisma genera la columna de lista sin `NOT NULL`.
- **Jest:** se agregó `moduleNameMapper` para resolver los imports `./x.js` del cliente generado a sus fuentes `.ts`.
- **`npm install` local con los scripts de instalación de Prisma bloqueados** (`allowScripts` de npm 12). La CLI funcionó igual para `generate` y `migrate diff`. En Docker, `npm ci` usa el npm de `node:24-alpine`.

## 7. Ambigüedades encontradas
- **Salas renombradas y seed:** el spec dice "seed idempotente con upsert" y S-07 permite al ADMIN renombrar salas. Un upsert por nombre crearía de nuevo la sala original tras un renombrado. Opción conservadora: las salas se crean **solo si la tabla `rooms` está vacía** (con `skipDuplicates`). Los usuarios sí usan upsert por email.
- **Nombres de usuarios, ubicación y equipamiento de las salas del seed:** el spec no los define. Se usó "Administrador RRHH" y "Empleado Uno/Dos/Tres"; ubicaciones "Piso 1–3"; equipamiento variado (D-25).
- **Longitud mínima de 1 carácter** en `name`, `title`, `reason` y `location`: el máximo lo impone `VARCHAR(n)`; el mínimo queda para la validación de la API (`ValidationPipe`, T02a en adelante). No se agregaron CHECK de longitud mínima.
- **`DATABASE_URL`:** no está en la tabla de parámetros del spec §5. Se declaró en el compose con default `postgresql://salalibre:salalibre@db:5432/salalibre`, coherente con los defaults de Postgres de T01.
- **`PrismaService` en `src/prisma/`** (lo pide el backlog) y no en `src/common/` (spec §10). Se siguió el backlog.
- **`HealthService` depende de `PrismaService` directamente,** sin interfaz por token. No es un repositorio de dominio, sino un chequeo de infraestructura.
