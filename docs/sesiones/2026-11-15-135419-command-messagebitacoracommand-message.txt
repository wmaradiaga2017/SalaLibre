● Definí el orden de los errores y lo agregué al spec §8, en una nueva
  subsección «Orden de validación». La API responde siempre el primer error que
  encuentra.

  Orden general: 401 (sesión) → 403 (rol) → 400 (formato) → 404 (no existe) →
  reglas de negocio.

  Crear reserva (POST /api/bookings):
  1. Sala inexistente → 404.
  2. Reglas de tiempo, que no consultan la base, en el orden de las RN:
     INVALID_SLOT → INVALID_DURATION → OUTSIDE_BUSINESS_HOURS → BOOKING_IN_PAST
     → TOO_FAR_AHEAD.
  3. Reglas que leen la sala: ROOM_INACTIVE → CAPACITY_EXCEEDED.
  4. DAY_CLOSED, dentro de la transacción y con el bloqueo por fecha.
  5. 409 BOOKING_CONFLICT, que da la base al insertar.

  Así no se abre una transacción para una petición que ya es inválida.

  BOOKING_ALREADY_STARTED. Si la reserva cumple las dos, "ya cancelada" informa
